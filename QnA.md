#### Why is Java so popular?


Java is popular because it provides a good balance of platform independence, reliability, performance, security, and a large ecosystem.

One of its biggest advantages is the JVM (Java Virtual Machine). Java code is compiled into bytecode, which can run on different operating systems as long as a compatible JVM is available. This is the basis of "write once, run anywhere."

Java also has strong object-oriented programming support, automatic garbage collection, exception handling, multithreading, and a large standard library, which makes it suitable for building large and maintainable applications.

Another major reason is its mature ecosystem. There are widely used frameworks such as Spring and Spring Boot, and Java is heavily used for enterprise applications, backend services, financial systems, and large-scale distributed systems.

Finally, Java has been around for a long time, so there is a large developer community, extensive documentation, mature tooling, and a huge amount of existing production code.

#### What is platform independence?
Platform independence means that a program can run on different operating systems without requiring changes to its source code.

Java achieves this primarily through bytecode and the JVM. When we compile Java source code, the Java compiler converts it into platform-independent bytecode rather than directly into machine code for a specific operating system.

That bytecode can then run on Windows, Linux, macOS, etc., as long as the corresponding JVM is installed.

This is why Java is commonly described as: `Write Once, Run Anywhere.`
```
Platform independence
        ↓
Same Java bytecode
        ↓
Can run on different OS
        ↓
Requires compatible JVM
        ↓
JVM handles OS-specific details
```

####  What is bytecode?
Bytecode is the intermediate instruction set generated by the Java compiler from Java source code. It's stored in .class files and is designed to be executed by the JVM. Since bytecode isn't tied to a specific operating system or CPU architecture, the same compiled bytecode can generally run on different platforms as long as a compatible JVM is available. The JVM can interpret the bytecode or use JIT compilation to convert parts of it into native machine code at runtime.

#### Compare JDK vs JVM vs JRE
JVM is responsible for running Java bytecode, JRE provides the environment required to run Java applications, and JDK provides everything required to develop and run Java applications.

In simple terms, JVM is the engine, JRE is the runtime environment, and JDK is the complete development kit.


#### What are the important differences between C++ and Java?
Both C++ and Java are object-oriented languages and have similar C-style syntax, but they differ significantly in how they handle memory, execution, inheritance, pointers, and platform compatibility.

C++ is generally compiled to native machine code and gives developers more direct control over memory and system resources. Java compiles to bytecode, which runs on the JVM, and provides automatic memory management through garbage collection.

Java also avoids direct pointer manipulation and supports single class inheritance, while C++ supports multiple inheritance through classes. Java's design focuses more on portability, managed memory, and application-level development, whereas C++ provides more low-level control and is commonly used where direct hardware or resource control is important.

#### What is the role for a classloader in Java?
A ClassLoader is a part of the JVM responsible for loading Java class bytecode into memory when the class is required. It locates the .class file, loads its bytecode into the JVM, and the JVM then links and initializes the class as required.

Class loading is generally lazy, meaning a class isn't necessarily loaded into the JVM simply because its .class file exists. It is typically loaded when the JVM needs the class.

Java also uses a hierarchy of class loaders, including the Bootstrap, Platform, and Application class loaders. This hierarchy provides separation and security and allows Java applications to use both core Java classes and application/dependency classes.


#### What are Wrapper classes?
Wrapper classes are the object representations of Java's primitive data types. They allow primitive values such as int, double, and boolean to be treated as objects when an object is required.

Java provides a corresponding wrapper class for each primitive type, such as Integer for int, Double for double, and Boolean for boolean.

They are particularly useful when working with collections and generic types, because Java generics work with reference types rather than primitive types.

Java also provides autoboxing and unboxing to automatically convert between primitives and their corresponding wrapper types. One thing to be careful about is that wrapper objects can be null, so automatic unboxing can potentially result in a NullPointerException.


#### What is autoboxing and unboxing?
Autoboxing is the automatic conversion of a primitive into its corresponding wrapper object, such as converting an int to an Integer. Unboxing is the reverse conversion, where an Integer is automatically converted back to an int. Java provides these conversions mainly to make it convenient to work between primitives and object-based APIs such as collections. For example, when we add an int to a List<Integer>, Java automatically boxes it into an Integer. One thing to be careful about is that unboxing a null wrapper can result in a NullPointerException.

#### What is casting?
Casting is converting a value or reference from one compatible type to another. For primitives, we commonly have widening conversions, such as int to double, which can happen implicitly, and narrowing conversions, such as double to int, which require explicit casting and may result in data loss. For reference types, we can upcast a child object to its parent type and downcast a parent reference back to a child type. Downcasting needs to be done carefully because if the actual object isn't of the target type, it can result in a `ClassCastException`.

`ClassCastException` is an unchecked runtime exception that occurs when an object is explicitly cast to an incompatible type. It's commonly seen with downcasting in inheritance. For example, if an Animal reference actually points to a Cat object and we try to cast it to Dog, the code can compile because Dog and Animal are related, but the JVM detects the actual object type at runtime and throws ClassCastException. We can avoid unsafe downcasts by checking with instanceof first.

#### Are all String’s immutable?  
Yes. String objects in Java are immutable, meaning once a String object is created, its character contents cannot be changed. Operations such as concatenation or replace() create a new String instead of modifying the existing object. This immutability enables safe String Pool sharing, makes Strings suitable as keys in hash-based collections, provides useful thread-safety characteristics, and is important for security-sensitive values. If we need to modify character data repeatedly, we'd generally use StringBuilder or StringBuffer instead.

#### Where are String values stored in memory?
String objects are stored on the heap. String literals are maintained in the String Pool, which is also part of the heap in modern Java. For example, with String s = "Java", the reference s refers to the pooled String object. If we use new String("Java"), a separate String object is explicitly created on the heap, although the literal "Java" itself can still be present in the String Pool. The String Pool allows Java to reuse identical immutable String literals.

#### What's the difference between String, StringBuffer and StringBuilder?
`String` is immutable, while `StringBuffer` and `StringBuilder` are mutable. If I repeatedly modify a String, new String objects can be created, so for frequent modifications I'd generally use a mutable buffer. StringBuilder is not synchronized and is usually preferred for single-threaded or non-shared use because it avoids synchronization overhead. StringBuffer provides synchronized methods, so it can be useful when synchronized access to the same mutable buffer is required across threads. In practice, I'd normally use String for immutable text and StringBuilder for constructing or modifying strings efficiently.

#### What is a class?
A class is a user-defined type that acts as a blueprint for creating objects. It defines the data an object can hold through fields and the behavior it can perform through methods. A class can also contain constructors, static members, nested types, and other members.

When we create an object using new, Java creates an instance of that class, and the instance gets its own state for the class's instance fields. 

#### What is an object?
An object is a runtime instance of a class. It represents a concrete entity that has state and behavior.

The class defines what data and operations an object can have, while the object actually holds the data and can perform those operations.

#### What is state of an object?
The state of an object is the current data or values held by its instance variables at a particular point in time.

#### What is behavior of an object?
The behavior of an object refers to the actions or operations that the object can perform. In Java, an object's behavior is primarily defined by the methods of its class.

#### What is the super class of every class in Java?
In Java, java.lang.Object is the root superclass of the class hierarchy. Every Java class directly or indirectly extends Object unless it's Object itself. If we don't explicitly specify a superclass, the compiler implicitly makes the class extend Object. Because of this, every class inherits common methods such as equals(), hashCode(), toString(), and getClass().

For example, if Dog extends Animal, and Animal doesn't explicitly extend anything, the hierarchy is Dog → Animal → Object.

One important distinction is that interfaces don't extend Object; Object is the root of the class hierarchy, not the interface hierarchy.

#### Explain about toString method ?
toString() is a public method defined in java.lang.Object that returns a string representation of an object. Every Java class inherits it, and in practice we often override it to provide a meaningful representation of the object's state.

The default implementation from Object returns a string based on the object's runtime class name and its hash code, which is usually not very useful for debugging. By overriding toString(), we can make logging, debugging, and console output much more readable.

Also, when we pass an object to System.out.println() or concatenate it with a String, Java can invoke toString() to obtain its textual representation.

```
class Employee {
    int id;
    String name;

    @Override
    public String toString() {
        return "Employee{id=" + id + ", name='" + name + "'}";
    }
}

public class Main {
    public static void main(String[] args) {

        Employee e = new Employee();
        e.id = 101;
        e.name = "Ritesh";

        System.out.println(e);

        String result = "Employee details: " + e;
        System.out.println(result);
    }
}
```

#### What is the use of equals method in Java?
equals() is used to compare two objects for logical equality rather than checking whether they are the exact same object in memory. It's defined in Object, and classes can override it to specify which fields determine equality.

For example, two Employee objects may be considered equal if they have the same employee ID, even though they are separate objects. This is different from ==, which for object references checks whether both references point to the same object.

When we override equals(), we generally also need to override hashCode() so that the equality and hashing contract remains consistent, especially when objects are used in collections such as HashMap and HashSet

```
equals() → Used to check logical equality between two objects.
Object.equals() → By default, equality is identity-based.
== → For objects, checks whether two references point to the same object.
equals() → Can be overridden to define equality based on object data/state.
String.equals() → Compares string contents, not references.
equals() + hashCode() → Must be consistent; equal objects must have the same hashCode().
HashSet/HashMap → Depend on both hashCode() and equals() for correct behavior.
equals(Object obj) → Must use Object parameter to properly override the method.
Mutable equality fields → Changing them while an object is in HashSet/HashMap can cause lookup problems.
```

#### What are the important things to consider when implementing equals method?
When implementing equals(), I first make sure the method follows the standard equality contract. I usually check reference equality first, handle null, verify that the other object is of a compatible type, and then compare only the fields that actually define logical equality for that class.

The important part is that equals() must be reflexive, symmetric, transitive, consistent, and return false when compared with null. I also always consider hashCode() because if two objects are equal, they must return the same hash code.

Another practical consideration is avoiding mutable fields in equality when possible, especially for objects that will be used as HashMap keys or stored in HashSet, because changing an equality-defining field after insertion can break lookup behavior.
```
class Employee {
    private final int id;
    private String name;

    public Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }

        if (!(obj instanceof Employee other)) {
            return false;
        }

        return this.id == other.id;
    }

    @Override
    public int hashCode() {
        return Integer.hashCode(id);
    }
}
```
Here, we've decided that id defines employee equality.

So:
```
Employee e1 = new Employee(101, "Ritesh");
Employee e2 = new Employee(101, "Rahul");

System.out.println(e1.equals(e2)); // true
```

Even though the names are different, they are considered equal because the application has defined id as the equality field.

- Define exactly what makes two objects logically equal, implement that consistently in equals(), and use the same equality-defining data in hashCode().

#### What is the Hashcode method used for in Java?
hashCode() is a method from the Object class that returns an integer value for an object. Its main purpose is to help hash-based collections such as HashMap and HashSet locate objects efficiently. The hash code is used to narrow down where an object should be stored or searched, and then equals() is used to check logical equality when necessary.

A hash code is not unique, so two different objects can have the same hash code. Also, if two objects are equal according to equals(), they must have the same hash code. That's why equals() and hashCode() are normally implemented together.

####  Explain inheritance with examples .
Inheritance is an object-oriented programming mechanism in which a child class acquires accessible fields and methods from a parent class. In Java, class inheritance is implemented using the extends keyword.

For example, if Dog extends Animal, then Dog inherits the accessible members of Animal and can also define its own behavior. This allows code reuse and represents an "is-a" relationship—for example, a Dog is an Animal.

Java supports single, multilevel, and hierarchical inheritance through classes, but it does not support multiple inheritance of classes. Multiple inheritance of type can be achieved using interfaces.

The child class can also override inherited methods to provide more specific behavior.

####  What is method overloading?
Method overloading is a form of compile-time polymorphism where a class has multiple methods with the same name but different parameter lists. The methods can differ in the number, type, or order of parameters. When a method is called, the compiler determines which overloaded version to invoke based on the arguments passed.

For example, a Calculator class can have multiple add() methods accepting two integers, three integers, or two doubles.

One important point is that changing only the return type does not constitute method overloading.

```
class Printer {

    void print(String text) {
        System.out.println(text);
    }

    void print(int number) {
        System.out.println(number);
    }

    void print(String text, int number) {
        System.out.println(text + number);
    }
}
```

#### What is method overriding?
Method overriding occurs when a subclass provides a specific implementation of a method that is already defined in its superclass. The overriding method must have a compatible signature, and the return type must be the same or a covariant subtype. It is mainly used to provide specialized behavior in the child class.

Method overriding is also the basis of runtime polymorphism. For example, if Dog overrides sound() from Animal, a reference of type Animal can point to a Dog object, and calling sound() will execute the Dog implementation at runtime.

We normally use the @Override annotation because it allows the compiler to verify that we are actually overriding a superclass method.
```
class Animal {

    void sound() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Dog barks");
    }
}

class Cat extends Animal {

    @Override
    void sound() {
        System.out.println("Cat meows");
    }
}
```
```
Overriding → Child class provides its own implementation of an inherited parent method.
Signature → Overriding method must have the same parameter list.
Return type → Same or covariant subtype.
Runtime polymorphism → Parent reference can call child implementation.
@Override → Recommended; compiler verifies the override.
Access modifier → Cannot reduce visibility.
private → Cannot be overridden.
static → Hidden, not overridden.
final → Cannot be overridden.
Constructor → Cannot be overridden.
Overloading → Same name + different parameters; compile-time.
Overriding → Same method + inheritance; runtime.
```
####  Can super class reference variable can hold an object of sub class?
Yes, a superclass reference variable can hold a subclass object. This is called upcasting and is a key part of runtime polymorphism. For example, Animal animal = new Dog(); is valid because a Dog is an Animal. The reference type determines which members are accessible at compile time, while the actual object type determines which overridden method implementation runs at runtime.

So in Animal animal = new Dog(), I can access methods defined in Animal, but if a method is overridden by Dog, the Dog implementation is selected at runtime. However, Dog-specific methods that are not present in Animal cannot be accessed directly through the Animal reference.
```
class Animal {

    void sound() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Dog barks");
    }

    void fetch() {
        System.out.println("Dog fetches the ball");
    }
}

public class Main {
    public static void main(String[] args) {

        Animal animal = new Dog();

        animal.sound();   // ✅ Dog barks
        // animal.fetch();   // ❌ Not accessible
    }
}
```
- The reference type controls what you are allowed to call; the actual object type controls overridden method behavior.
```
Superclass reference → Can hold subclass object.
Animal a = new Dog() → Valid upcasting.
Reference type → Determines accessible members at compile time.
Actual object type → Determines overridden method implementation at runtime.
Dog-specific method → Cannot be called through Animal reference unless cast.
Upcasting → Usually implicit and safe.
Runtime polymorphism → Same parent reference can refer to different child objects.
```
#### Is multiple inheritance allowed in Java?
Java does not support multiple inheritance of classes, meaning a class cannot extend more than one class. The main reason is to avoid ambiguity in cases where multiple parent classes provide conflicting implementations, commonly referred to as the diamond problem.

However, Java supports multiple inheritance of type through interfaces. A class can implement multiple interfaces, and Java provides rules for resolving conflicts, especially when interfaces contain default methods.

For example, class Duck implements Flyable, Swimmable is valid, whereas class Duck extends Animal, Bird is not.
```
interface Camera {
    void takePhoto();
}

interface GPS {
    void getLocation();
}

class Smartphone implements Camera, GPS {

    @Override
    public void takePhoto() {
        System.out.println("Taking photo");
    }

    @Override
    public void getLocation() {
        System.out.println("Getting location");
    }
}
```
```
Multiple class inheritance → ❌ Java doesn't allow `extends A, B`.
Reason → Avoids ambiguity/diamond problem.
Multiple interfaces → ✅ A class can implement multiple interfaces.
`implements` → Used for multiple interface inheritance.
default method → Interface provides implementation; implementing class need not override it.
No override → Default implementation is inherited and available.
Override → Child can provide its own implementation.
Abstract interface method → Concrete child must implement it.
Java supports → Single class inheritance + multiple interface implementation.
```
- If an interface contains an abstract method, a concrete implementing class must provide an implementation for that method. If the class doesn't want to implement it yet, the class itself can be declared abstract and pass that responsibility to its subclass. Another option is that the interface can provide a default implementation, in which case the implementing class is not required to override the method and can simply inherit the default behavior.

#### What is an interface?
An interface in Java is a contract that defines a set of behaviors that implementing classes are expected to provide. A class implements an interface using the implements keyword. Interfaces are mainly used to achieve abstraction, loose coupling, and polymorphism, and they allow a class to implement multiple interfaces.

An interface can contain abstract methods, and since Java 8 it can also contain default and static methods with implementations. It can also contain constants, which are implicitly public, static, and final.

For example, if we have a Payment interface with processPayment(), classes such as UpiPayment and CardPayment can implement that contract differently. This lets the application depend on the Payment interface rather than a specific implementation.

#### What is an abstract class?
An abstract class is a class declared with the abstract keyword that is intended to be used as a superclass rather than instantiated directly. It can contain both abstract methods, which subclasses must implement, and concrete methods with shared implementation. It can also have instance variables, constructors, static methods, and other normal class members.

An abstract class is useful when related classes share common state or implementation but also need to provide their own specific behavior. For example, an abstract Animal class can provide common methods like eat() while declaring sound() abstract, leaving each subclass such as Dog or Cat to implement it.
```
Abstract class cannot be instantiated directly.
Abstract class does NOT have to contain an abstract method.
Abstract class CAN have constructors.
Abstract class CAN have concrete methods.
Concrete subclass must implement inherited abstract methods.
Abstract subclass can leave abstract methods unimplemented.
A class can extend only one class, abstract or otherwise.
```

#### When do you use an abstract class?
I use an abstract class when I have a group of closely related classes that share common state or implementation, but some behavior needs to be specialized by each subclass. It lets me put the common functionality in the parent while using abstract methods to force subclasses to provide the parts that are different.

For example, if I have different types of employees, the abstract Employee class can contain common fields like name and salary and common methods like showDetails(), while leaving something like calculateBonus() abstract because each employee type may calculate it differently.

I would prefer an abstract class when the subclasses have a genuine common base and need shared implementation or state. If I only need to define a contract or capability without requiring shared state, an interface is usually more appropriate.

#### How do you define an abstract method?
An abstract method is a method that is declared using the abstract keyword but does not have a method body. It is used when the parent class knows that a particular behavior must exist, but the actual implementation should be provided by subclasses. A concrete subclass must implement the inherited abstract method. Abstract methods can be declared only in abstract classes or interfaces.

For example, abstract void sound(); declares the behavior, and subclasses like Dog or Cat provide their specific implementations.

```
abstract class Animal {

    abstract void sound();

    void eat() {
        System.out.println("Animal is eating");
    }
}

class Dog extends Animal {

    @Override
    void sound() {
        System.out.println("Dog barks");
    }
}
```
```
Abstract method → Declared with abstract keyword and no method body.
Syntax → abstract void sound();
Semicolon → Abstract method declaration ends with ;.
Where allowed → Abstract class or interface.
Concrete subclass → Must implement it.
Abstract subclass → Can leave it unimplemented.
abstract + final → Not allowed.
abstract + static → Not allowed.
abstract + private → Not allowed.
Purpose → Parent defines WHAT behavior is required; subclass defines HOW.
```

####  Compare abstract class vs interface?
The main difference is that an abstract class is used when related classes share common state or implementation, whereas an interface is primarily used to define a contract or capability.

An abstract class can have instance variables, constructors, concrete methods, and abstract methods, and a class can extend only one superclass. An interface doesn't have per-object instance state and its fields are implicitly public static final; modern interfaces can contain abstract, default, static, and private methods. A class can implement multiple interfaces.

So, if I need to share state and common implementation among closely related classes, I would consider an abstract class. If I need a common contract that can be implemented by different or unrelated classes, I would generally use an interface.

#### What is a constructor?
A constructor is a special member of a class that is automatically invoked when an object is created. Its main purpose is to initialize the object's initial state. A constructor has the same name as the class and doesn't have a return type. Constructors can be overloaded, so a class can provide different ways of initializing its objects. If we don't declare any constructor, the compiler provides a default no-argument constructor, provided no other constructor has been declared.

For example, in a Student class, a parameterized constructor can initialize fields like name and age at the time the object is created.
```

Main purpose → Initialize object's initial state.

super() → Calls superclass constructor; must be first statement.
Inheritance → Constructors are not inherited.
Overriding → Constructors cannot be overridden.
static/final/abstract → Not allowed for constructors.
private constructor → Allowed; can restrict object creation.
```
#### What is a default constructor?
A default constructor is the no-argument constructor that the compiler automatically provides when a class does not declare any constructor. It initializes the object using the normal default initialization rules and implicitly invokes the superclass no-argument constructor. An important point is that once we declare any constructor ourselves, the compiler stops providing the default constructor.

For example, if I have a class with no constructor, new Student() works because the compiler supplies a default constructor. But if I declare only a parameterized constructor, I have to explicitly define a no-argument constructor if I still want new Student() to work.

#### How do you call a super class constructor from a constructor?
We use the super() keyword to call a superclass constructor from a subclass constructor. The arguments passed to super() must match an accessible constructor in the parent class, and the super() call must be the first statement in the child constructor. If we don't explicitly write a super() call, Java implicitly inserts a no-argument super() call, provided the parent class has an accessible no-argument constructor.

For example, if Animal has a constructor accepting a name, then Dog can call it using super(name). This allows the parent class to initialize the part of the object that belongs to the parent class before the child constructor continues.
```
class Animal {

    String name;

    Animal(String name) {
        System.out.println("Animal constructor");
        this.name = name;
    }
}

class Dog extends Animal {

    Dog(String name) {
        super(name);
        System.out.println("Dog constructor");
    }
}
```
```
super(...) → Calls a superclass constructor.
First statement → super(...) must be first in child constructor.
No explicit super() → Compiler inserts super() automatically if parent has accessible no-arg constructor.
Parent constructor → Executes before child constructor body.
Parent has only parameterized constructor → Child must explicitly call it with super(arguments).
this(...) → Calls another constructor in the same class.
super(...) vs this(...) → Cannot both be first statements in the same constructor.
```

#### What is the use of this()?
this() is used to call another constructor of the same class. It's mainly used for constructor chaining, so we can centralize initialization logic and avoid duplicating code across multiple constructors. The this() call must be the first statement in the constructor, and the target constructor must be an accessible constructor of the same class.

For example, a no-argument constructor can call a parameterized constructor using this("Unknown", 0), allowing all the actual initialization to happen in one place.
```
class Employee {

    String name;
    int id;
    String department;

    Employee() {
        this("Unknown", 0, "General");
    }

    Employee(String name, int id) {
        this(name, id, "General");
    }

    Employee(String name, int id, String department) {
        this.name = name;
        this.id = id;
        this.department = department;
    }
}
```
```
this() → Calls another constructor of the same class.
Main use → Constructor chaining and avoiding duplicate initialization code.
this() → Must be the first statement of the constructor.
super() → Calls the parent-class constructor.
this(...) and super(...) → Cannot both be first in the same constructor.
Constructor chaining → One constructor calls another constructor, which may eventually call super().
```

#### Can a constructor be called directly from a method?
No, a constructor cannot be called directly from a method like a normal method. A constructor is invoked as part of object creation, typically using the new keyword. If I need to initialize another object inside a method, I create that object using new, which causes its constructor to execute.

The only way constructors can explicitly invoke other constructors is through constructor chaining using this() or super(), and those calls are restricted to constructors themselves.

#### Is a super class constructor called even when there is no explicit call from a sub class constructor?
Yes. Every time a subclass object is created, a superclass constructor is invoked as part of the construction process. If the subclass constructor doesn't explicitly call super(...), Java implicitly inserts a no-argument super() call as the first statement. However, this is possible only if the superclass has an accessible no-argument constructor. If the superclass has only parameterized constructors, the subclass must explicitly call one using super(arguments).

This ensures that the superclass portion of the object is initialized before the subclass-specific initialization takes place.

####  What is polymorphism?
Polymorphism means the ability of the same interface or method call to represent different behaviors depending on the situation. In Java, the two main forms are compile-time polymorphism through method overloading and runtime polymorphism through method overriding.

For runtime polymorphism, a superclass or interface reference can point to different subclass objects, and when an overridden method is called, Java selects the implementation based on the actual object at runtime. For example, Animal animal = new Dog() and animal.sound() executes Dog's implementation if Dog overrides sound().

Polymorphism is important because it allows code to depend on abstractions such as a superclass or interface rather than tightly coupling it to a specific implementation.

#### What is the use of instanceof operator in Java?
The instanceof operator is used to check whether an object is an instance of a particular type, including a class, subclass, or interface. It returns a boolean result and is commonly used when we need to safely perform a downcast or handle different implementations polymorphically.

For example, if Animal animal = new Dog(), animal instanceof Dog returns true because the actual object is a Dog. I can then safely cast it to Dog. It also works with interfaces, so it's useful when the runtime type of an object needs to be checked before performing type-specific operations.

One important point is that instanceof checks the actual runtime object against the target type; it doesn't simply check the reference variable's declared type.
```
instanceof → Checks whether an object is compatible with a given type.
Return type → boolean.
Works with → Classes, subclasses, and interfaces.
Common use → Check before downcasting.
Actual object → `instanceof` checks the runtime object type, not just reference type.
Superclass → Dog instanceof Animal is true.
null → `null instanceof Type` returns false.
Pattern matching → `obj instanceof Dog dog` combines checking + casting.
instanceof vs getClass() → instanceof allows hierarchy; getClass() checks exact runtime class.
```

#### What is coupling?
Coupling refers to the degree of dependency between classes or modules. If one class is heavily dependent on the implementation details of another class, we call it tight coupling. If it depends mainly on an abstraction and can work with different implementations without significant changes, that's loose coupling.

In Java, we commonly reduce coupling by using interfaces, dependency injection, and composition instead of directly creating concrete dependencies inside a class. For example, an OrderService depending on a Payment interface is more loosely coupled than directly depending on UpiPayment. Loose coupling makes code easier to test, maintain, replace, and extend.

**Tight Coupling:**
```
class UpiPayment {
    void processPayment() {
        System.out.println("UPI payment");
    }
}

class OrderService {

    private UpiPayment payment = new UpiPayment();

    void placeOrder() {
```

#### What is encapsulation?
Encapsulation is the mechanism of bundling an object's state and behavior together and restricting direct access to its internal state. In Java, this is commonly achieved by making fields private and exposing controlled public methods such as getters, setters, or business methods.

The important point is that encapsulation isn't just about making fields private; it's about controlling how the object's state can be accessed and changed. For example, instead of exposing a bank account's balance directly, I can provide a deposit() method that validates the amount before modifying the balance. This protects the object's invariants and reduces unnecessary coupling to its internal representation.
```
Encapsulation → Bundle state + behavior and control access to internal state.
Common technique → private fields + controlled public methods.
private → Prevents direct external access to the field.
Getter/setter → Possible tools, but encapsulation is not simply getters/setters.
Business methods → Often better than unrestricted setters because they enforce rules.
Main benefit → Protects object invariants and reduces coupling.
Abstraction → Hides unnecessary implementation details; encapsulation controls access.
```

#### What is an inner class?
An inner class is a class declared inside another class. It's generally used when the nested class is tightly related to the enclosing class and its implementation doesn't need to be exposed as an independent top-level class. A non-static inner class is associated with an instance of the outer class and can directly access its instance members, including private members.

Java actually has several forms of nested classes, including non-static inner classes, static nested classes, local classes, and anonymous classes. One important distinction is that only a non-static nested class is technically called an inner class; static nested classes are nested classes but not inner classes.
```
Inner class → Non-static class declared inside another class.
Outer class → Class containing the inner class.
Non-static inner class → Associated with an outer-class object.
Inner class → Can directly access outer instance members, including private ones.
Nested class → General term for any class declared inside another class.
Static nested class → Nested but NOT technically an inner class.
Static nested class → Doesn't require an outer-class object.
Local class → Declared inside a method/block.
Anonymous class → Class without a name, usually for one-time use.
Lambdas → Often replace anonymous classes for functional interfaces.
```

#### What is a static inner class?
A static inner class, technically called a static nested class, is a class declared inside another class with the static keyword. Unlike a non-static inner class, it doesn't hold an implicit reference to an instance of the outer class, so we can create it without creating an outer-class object.

It can directly access the outer class's static members, but it cannot directly access the outer class's instance members because there is no specific outer object associated with it. It's useful for grouping a helper or closely related type inside another class without requiring an enclosing object.

```

    String location = "Delhi";

    static class Employee {

        void display() {
            System.out.println(companyName); // ✅
            // System.out.println(location); // ❌
        }
    }
}
```
Creating the object:
```

employee.display();
```

because companyName is static.

But it cannot directly access:

`location`

because location belongs to a particular Company object.

A local class can access members of the enclosing class, and it can also access local variables from the enclosing method if those variables are final or effectively final. It's useful when a small helper type is needed only within a specific piece of logic.


### Modifiers

####  What is default class modifier?
If no access modifier is specified for a class, it has package-private, also called default access. This means the class is accessible only to other classes in the same package. default isn't a keyword being applied to the class; it refers to the access level when no modifier is specified. For a top-level class, the other available access level is public, while private and protected aren't allowed.
```
No class modifier → package-private/default access.
Package-private → Accessible only within the same package.
default → Not a keyword for this access level; it means no explicit modifier.
Top-level class → Can be public or package-private only.
Top-level class → Cannot be private or protected.
Nested class → Can have private/protected/default/public.
```

#### What is private access modifier?  
private is the most restrictive access modifier in Java. A private field, method, constructor, or nested class can be accessed only from within the class where it is declared. It is commonly used to hide internal implementation details and protect an object's state, which supports encapsulation. For example, I would typically keep a field like balance private and expose controlled operations such as deposit() or withdraw() instead of allowing direct modification.
```
private → Most restrictive access modifier.
Access → Only within the class where declared.
Package access → Other classes in same package cannot directly access it.
Subclass access → Not directly accessible in child class.
Use → Encapsulation and hiding implementation details.
Can be used with → fields, methods, constructors, nested classes.
Top-level class → Cannot be private.
```

#### What is default or package access modifier?
Default access, technically called package-private access, is the access level you get when no access modifier is specified. The member is accessible to other classes in the same package, but not directly accessible from classes in a different package. It's commonly used when classes or members are intended to be shared internally within a package rather than exposed as part of the public API.

For example, if I declare class Employee without an access modifier, other classes in the same package can use it, while classes from another package cannot directly access it.

#### What is protected access modifier?
protected provides access to a member from all classes in the same package and from subclasses, including subclasses in other packages. The important difference from package-private is the cross-package inheritance rule: a subclass in another package can access the protected member through its inherited context, but it doesn't get unrestricted access to that member through any arbitrary superclass object.

It's useful when a class wants to expose certain implementation details to its subclasses and package-level collaborators, while keeping those members hidden from unrelated classes in other packages.
```
protected → Accessible in same package + subclasses in other packages.
Same package → protected behaves like package-private access.
Different package → Access comes through inheritance.
Arbitrary superclass object → Not freely accessible from a cross-package subclass.
Top-level class → Cannot be protected.
Nested class → Can be protected.
Use → Expose controlled functionality/state to subclasses and package collaborators.
```

#### What is public access modifier?
public is the least restrictive access modifier in Java. A public member can be accessed from any class, including classes in different packages, provided the enclosing class is accessible. It's commonly used for APIs and methods that are intentionally exposed to other parts of the application.

For example, a public service method can be called from another package. However, I wouldn't make fields public unnecessarily because that exposes the internal state directly; I'd generally keep state private and expose controlled public methods instead.

#### What access types of variables can be accessed from a class in same package?
If a class is in the same package as another class, it can directly access that class's public, protected, and package-private members. It cannot directly access private members because private access is restricted to the declaring class itself.

So, within the same package, protected behaves similarly to package-private access; the additional protected privilege is that subclasses can also access it across package boundaries.

#### What access types of variables can be accessed from a class in different package?
From a class in a different package, public members are directly accessible. private and package-private members are not accessible. protected is accessible only through inheritance when the accessing class is a subclass, and cross-package protected access has some additional restrictions compared with same-package access. So, for an unrelated class in another package, only public members are directly accessible.
```
Different package + unrelated class → public ✅ only.
Different package + subclass → public ✅ and protected ✅.
Package-private/default → Same package only.
private → Declaring class only.
protected → Same package OR subclass access across packages.
```

#### What access types of variables can be accessed from a sub class in same package?
If a subclass is in the same package as its superclass, it can directly access the superclass's public, protected, and package-private members. It cannot directly access private members because private access is restricted to the class that declares the member.

So in this case, inheritance doesn't give any additional restriction for protected members because same-package access already allows them. The important distinction appears when the subclass is in a different package.
```
Subclass + same package → public ✅, protected ✅, default ✅, private ❌.
private → Only declaring class.
protected → Accessible through same-package access or inheritance.
```

#### What access types of variables can be accessed from a sub class in different package?
When a subclass is in a different package from its superclass, it can directly access the superclass's public and protected members. It cannot directly access private or package-private members. The important point with protected access is that, across package boundaries, access is provided through the inheritance relationship rather than ordinary package access.

So for a subclass in another package, the practical rule is public plus protected; default and private are not directly accessible.
```
Subclass + different package → public ✅, protected ✅, default ❌, private ❌.
protected → Accessible across packages through inheritance.
default/package-private → Same package only.
private → Declaring class only.
Cross-package protected → Not unrestricted access through any Parent object.
```


#### What is the use of a final modifier on a class?
The final modifier on a class prevents the class from being inherited or extended. We use it when we don't want subclasses to modify or extend the class's behavior, which can help preserve class invariants, enforce design constraints, and sometimes provide security benefits. A common example is String, which is final in Java.

One important point is that final does not make the objects of the class immutable by itself. It only prevents inheritance.
```
final class → Cannot be extended/inherited.
Main use → Prevent subclassing and preserve intended design/invariants.
Example → String is a final class.
Instantiation → final classes can still be instantiated.
final ≠ immutable → final prevents inheritance, not state changes.
Security/design → Can prevent subclasses from overriding/extending behavior.
abstract + final → Not allowed together.
```

#### What is the use of a final modifier on a method?
The final modifier on a method prevents that method from being overridden by subclasses. The method can still be inherited and called normally, but a subclass cannot provide a different implementation for it. We use it when a particular behavior must remain consistent across the inheritance hierarchy, such as when the parent class needs to enforce an important invariant or workflow.
```
final method → Cannot be overridden by a subclass.
Can be inherited → Yes.
Can be called → Yes.
Can be overloaded → Yes.
Main use → Prevent subclasses from changing specific behavior.
final class → Prevents inheritance entirely.
final variable → Prevents reassignment.
```

#### What is a final variable?
A final variable is a variable that can be assigned only once. After initialization, it cannot be reassigned. For a primitive, this means its value cannot change. For an object reference, the reference cannot point to another object, although the referenced object's internal state may still be mutable.

A final variable can be initialized at declaration time, in a constructor for an instance field, or in an initialization block depending on where it's declared. When a static final variable represents a constant, we conventionally use uppercase names such as MAX_RETRY_COUNT.
```
final variable → Can be assigned only once.
Primitive + final → Value cannot be changed/reassigned.
Object reference + final → Reference cannot point to another object; object may still be mutable.
Final field → Can be initialized at declaration, initialization block, or constructor as appropriate.
Blank final → final field declared without initial value; must be definitely assigned before construction completes.
static final → Common way to define class-level constants.
final parameter → Parameter cannot be reassigned inside the method.
final ≠ immutable → Final reference can still point to a mutable object.
```

#### What is a final argument?
A final parameter is a method or constructor parameter that cannot be reassigned inside that method or constructor. It is mainly used when we want to prevent accidental reassignment of the parameter variable. For primitive parameters, the value can't be reassigned; for object parameters, the reference can't be changed to point to another object, although the object's internal state may still be modified.

Also, technically, final applies to the parameter variable, not to the argument passed by the caller.
```
final parameter → Cannot be reassigned inside the method/constructor.
Primitive parameter → Value cannot be reassigned.
Object parameter → Reference cannot be reassigned; object may still be mutable.
Technical term → `final` applies to the parameter, not the caller's argument.
Use → Prevent accidental reassignment inside the method.
```

#### What happens when a variable is marked as volatile?
When a field is declared volatile, it tells the Java Memory Model that the field can be accessed by multiple threads and that reads and writes to it must have the required cross-thread visibility and ordering guarantees. A write to a volatile variable happens-before a subsequent read of that same variable.

However, volatile does not provide mutual exclusion or make compound operations atomic. For example, volatile int count; count++ is still not thread-safe because increment is a read-modify-write operation. I would typically use volatile for simple state or flags where visibility is the main requirement, and use synchronization or atomic classes when I need atomic compound operations.
```
volatile → Mainly provides cross-thread visibility and ordering for a field.
Happens-before → Volatile write happens-before a subsequent read of the same variable.
Visibility → Other threads can observe updates reliably.
Atomicity → volatile does NOT make compound operations atomic.
count++ → Not thread-safe even when count is volatile.
Use case → Simple shared state/flags such as shutdown or running status.
synchronized → Provides mutual exclusion in addition to visibility/ordering.
volatile reference → Makes the reference volatile, not necessarily the referenced object's state.
Scope → volatile applies to fields, not local variables or parameters.
```

#### What is a static variable?
A static variable is a class-level variable, meaning it belongs to the class rather than to individual objects. Only one logical copy is associated with the class, and all objects of that class share it. It's useful when a value represents something common to all instances, such as a company name, configuration value, or instance counter. We normally access it using the class name, like Employee.company.

Unlike an instance variable, a static variable doesn't get a separate copy for every object. Also, static variables can be accessed from static methods directly, whereas instance variables require an object.
```
Static variable → Class-level variable shared by all objects.
Instance variable → Separate copy for each object.
static → Shared, not constant.
static final → Common pattern for constants.
Access → Prefer ClassName.variable.
Static method → Can directly access static variables.
Static method → Cannot directly access instance variables without an object.
Use cases → Shared configuration, counters, constants, class-level state.
```

### Collections

#### Why do we need collections in Java?
We use collections in Java when we need to store and work with multiple objects. Unlike arrays, collections can grow or shrink dynamically and provide different types of data structures based on our requirement.

For example, we use a `List` when we want to maintain order, a `Set` when we don't want duplicates, and a `Map` when we want to store data as key-value pairs.

Collections also provide ready-made methods for adding, removing, searching, and sorting data, so we don't have to implement these operations ourselves.

In real applications, collections are used everywhere, such as storing users, database results, or mapping IDs to objects.
```
Collections → Used to store/manage groups of objects.
Main advantage → Flexible data structures + ready-made operations.
Array → Fixed size.
List → Ordered, duplicates allowed.
Set → Unique elements.
Map → Key-value pairs; Map is not a subtype of Collection.
Queue → Designed for ordered processing.
Dynamic sizing → Collections can grow/shrink as needed.
Generics → Provide type safety, e.g. List<String>.
Backend use → Users, database results, IDs, tasks, configuration, etc.
```

#### What are the important interfaces in the collection hierarchy?
The main interfaces in the Java Collection hierarchy are Collection, List, Set, Queue, and Deque. Collection provides common operations for groups of objects. List is used when we need ordered data and can allow duplicates, Set is used for unique elements, Queue is used for processing elements in a particular order, and Deque allows operations from both ends.

There is also Map, which is part of the Java Collections Framework, but it is not a child of the Collection interface because it stores data as key-value pairs.

#### What are the important methods that are declared in the collection interface?
The `Collection` interface provides common methods that are used to work with a group of objects. The important ones are `add()`, `remove()`, `contains()`, `size()`, `isEmpty()`, `clear()`, and `iterator()`.

For adding multiple elements, we have `addAll()`, and for checking multiple elements, we have `containsAll()`. These methods are common across collection types like `List`, `Set`, and `Queue`, although their exact behavior can differ depending on the implementation.
```
add() → Adds one element.
addAll() → Adds multiple elements.
remove() → Removes an element.
removeAll() → Removes matching elements from another collection.
contains() → Checks whether an element exists.
containsAll() → Checks whether all given elements exist.
size() → Returns number of elements.
isEmpty() → Checks whether collection has no elements.
clear() → Removes all elements.
iterator() → Used to traverse the collection.
```

#### Can you explain briefly about the List interface?
List is an interface in the Java Collections Framework that we use when we need to store multiple elements in a specific order. It maintains insertion order, allows duplicate elements, and provides index-based access, so we can get or update an element using its position. Common implementations are ArrayList, LinkedList, and Vector. In practice, ArrayList is usually my default choice when I need a general-purpose list, while I would choose another implementation based on the specific requirement.
```
List → Ordered collection of elements.
Order → Insertion order is maintained.
Duplicates → Allowed.
Index → Supports index-based access.
Common implementations → ArrayList, LinkedList, Vector.
ArrayList → Common default choice.
List can contain null → Generally yes, depending on implementation.
```

#### Explain about ArrayList with an example?
ArrayList is a resizable array implementation of the List interface. I would use it when I need an ordered collection that allows duplicates and provides fast index-based access. Its size grows automatically as elements are added, unlike a normal array.

Internally, it uses an array, and when the current capacity is not enough, it grows the underlying array and copies the existing elements. Reading an element by index is efficient, while inserting or removing elements in the middle can be more expensive because the remaining elements may need to be shifted.

For that reason, ArrayList is usually my default List implementation unless I have a specific requirement that makes another implementation more suitable.
```
get(index) → O(1) average; direct index-based access.
add(element) → O(1) amortized; occasional resize makes one addition more expensive.
add(index, element) → O(n); elements may need to shift.
remove(index) → O(n); elements may need to shift.
contains(element) → O(n); searches through elements.
```
ArrayList is very good for reading/accessing elements by index, but inserting or removing elements in the middle is relatively expensive.

```
ArrayList → Resizable-array implementation of List.
Order → Maintains insertion order.
Duplicates → Allowed.
Index access → Fast, O(1) average.
Size → Grows automatically.
Internal structure → Backed by an array.
Middle insert/remove → O(n) because elements may shift.
End add → O(1) amortized.
```

#### How do you iterate around an ArrayList using iterator?
To iterate over an ArrayList using an Iterator, I first call the iterator() method on the list, which returns an Iterator. Then I use hasNext() to check whether another element is available and next() to retrieve it.

One advantage of using an iterator is that it provides a standard way to traverse collections, and it also allows safe removal of elements during iteration using iterator.remove(). This is preferable to directly modifying the list while iterating, which can otherwise result in a ConcurrentModificationException.
```
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;

class Main {
    public static void main(String[] args) {

        List<String> names = new ArrayList<>();

        names.add("Ritesh");
        names.add("Rahul");
        names.add("Aman");

        Iterator<String> iterator = names.iterator();

        while (iterator.hasNext()) {
            String name = iterator.next();
            System.out.println(name);
        }
    }
}
```
```
import java.util.ArrayList;
import java.util.Iterator;
import java.util.List;

class Main {

}
```

#### How do you sort an ArrayList?
For an ArrayList, I can sort the elements using Collections.sort() or, in modern Java, the List.sort() method. By default, elements are sorted according to their natural ordering, such as numbers in ascending order or strings alphabetically. If I need a different order, I can provide a Comparator.

For example, Collections.sort(numbers) sorts a list of integers in ascending order, while numbers.sort(Comparator.reverseOrder()) sorts them in descending order. For custom objects, I would normally use a Comparator to define the sorting logic based on the required field.
```

import java.util.Collections;
import java.util.List;

        numbers.add(40);
        numbers.add(10);
        numbers.add(30);
        numbers.add(20);

        Collections.sort(numbers); or numbers.sort(Comparator.naturalOrder()); // [10, 20, 30, 40]

        System.out.println(numbers);
    }
}
```

#### How do you sort elements in an ArrayList using comparable interface?
To sort an ArrayList using Comparable, I make the element class implement Comparable<T> and provide the natural ordering in the compareTo() method. Then I can use Collections.sort() or list.sort(null) to sort the list.

For example, if I want Employee objects to be sorted by employee ID, I implement compareTo() using the ID. compareTo() returns a negative value when the current object should come before the other object, zero when they are equal for ordering, and a positive value when it should come after.

I use Comparable when the class itself has a clear default or natural ordering. If I need different sorting rules, I would generally use a Comparator instead.
```
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

class Employee implements Comparable<Employee> {

    int id;
    String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.id, other.id);
    }

    @Override
    public String toString() {
        return id + " - " + name;
    }
}
```
```
List<Employee> employees = new ArrayList<>();

employees.add(new Employee(103, "Aman"));
employees.add(new Employee(101, "Ritesh"));
employees.add(new Employee(102, "Rahul"));

Collections.sort(employees);

System.out.println(employees); // [101 - Ritesh, 102 - Rahul, 103 - Aman]
```
```
Comparable → Defines a class's natural/default sorting order.
implements Comparable<Employee> → Class becomes comparable to another Employee.
compareTo() → Defines how two objects should be ordered.
negative → this comes before other.
0 → equal for ordering.
positive → this comes after other.
Collections.sort(list) → Uses Comparable's natural ordering when no Comparator is supplied.
list.sort(null) → Also uses natural ordering.

```
#### How do you sort elements in an ArrayList using comparator interface?
Comparator is used when I want to define custom sorting logic separately from the class being sorted. I create a Comparator<T> that compares two objects and then pass it to Collections.sort() or the list's sort() method.

For example, if I have an Employee list, I can create one comparator to sort by salary, another by name, and another by ID. This is more flexible than Comparable, where the class itself defines one natural ordering.

In modern Java, I would commonly use methods like Comparator.comparing(), comparingInt(), or comparingDouble() to make these comparators concise and readable.
```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class Employee {
    int id;
    String name;
    double salary;

    Employee(int id, String name, double salary) {
        this.id = id;
        this.name = name;
        this.salary = salary;
    }

    @Override
```

#### What is linkedList? What interfaces does it implement? How is it different from an ArrayList?
LinkedList is a doubly linked list implementation of the List and Deque interfaces. It stores elements as nodes, where each node keeps references to the previous and next node. #### Explain the BlockingQueue interface?
BlockingQueue is a thread-safe queue designed mainly for communication between multiple threads. Its main feature is that certain operations can block when the queue is full or empty. For example, put() waits if a bounded queue is full, and take() waits if the queue is empty.

It is commonly used in producer-consumer scenarios, where one or more threads produce tasks or data and other threads consume them. Common implementations include ArrayBlockingQueue, LinkedBlockingQueue, and PriorityBlockingQueue.

I would use a BlockingQueue when I need thread-safe coordination between producers and consumers rather than manually managing wait() and notify() logic.

Example:
```
BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

queue.put(100);        // may wait if full
int value = queue.take(); // may wait if empty
```

**Producer-Consumer Example**
```
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

public class Main {

    public static void main(String[] args) {

        BlockingQueue<String> queue =
                new ArrayBlockingQueue<>(2);

        Thread producer = new Thread(() -> {
            try {
                queue.put("Task 1");
                queue.put("Task 2");
                queue.put("Task 3");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                Thread.sleep(2000);

                System.out.println(queue.take());
                System.out.println(queue.take());
                System.out.println(queue.take());

            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
    }
}
```

The queue has capacity 2.

So when the producer tries to add "Task 3":
```
Task 1 → queue
Task 2 → queue
Task 3 → producer waits
             ↓
       consumer takes one
             ↓
       space becomes available
             ↓
       producer continues
```
That's the main idea behind BlockingQueue.

#### What is a priorityQueue?
PriorityQueue is a Queue implementation where elements are processed according to their priority rather than insertion order. By default, the smallest element according to natural ordering has the highest priority, but we can provide a Comparator to define a different priority.

For example, if I add 30, 10, and 20, calling poll() returns 10 first, then 20, then 30. Internally, it uses a priority-heap structure, which makes retrieving the highest-priority element efficient. I would use PriorityQueue when the next element to process should be based on priority rather than simple FIFO order.
```

queue.add(10);
queue.add(20);

System.out.println(queue.poll()); // 10
System.out.println(queue.poll()); // 20
System.out.println(queue.poll()); // 30
```

#### Explain about copyonwrite concurrent collections approach?
Copy-on-Write is a concurrency approach where a collection creates a new copy of its underlying data whenever a write happens, instead of modifying the existing data in place. The main advantage is that reads can happen without the same locking overhead, making it useful when reads are much more frequent than writes.

So I would use Copy-on-Write for relatively small collections that are read frequently and updated rarely, such as listener lists or configuration-style data. I would avoid it for write-heavy collections.

#### What is compareandswap approach?
Compare-and-Swap, or CAS, is a synchronization technique where a thread updates a value only if the current value is still equal to an expected value. If another thread has changed the value in the meantime, the CAS operation fails instead of overwriting it.

CAS is commonly used in Java's atomic classes such as AtomicInteger, AtomicLong, and AtomicReference. It allows certain updates to be performed without traditional locking, which can reduce thread contention and improve scalability for suitable workloads.

For example, compareAndSet(expected, update) changes the value only when the current value matches expected. If it doesn't match, the operation returns false, and the code can retry or handle the failure.
```

Success → Expected == current value → update happens.
Failure → Expected != current value → update doesn't happen.
CAS → Common foundation for atomic/concurrent operations.
Java examples → AtomicInteger, AtomicLong, AtomicReference.
CAS vs synchronized → CAS is lock-free at the operation level; synchronized uses locking.
CAS ≠ always faster → Heavy contention can cause repeated retries.
CAS → Good for small atomic state updates.
```

A lock is a synchronization mechanism used to control access to shared resources when multiple threads are running. Java provides the Lock interface, commonly implemented by ReentrantLock, which gives us explicit control over acquiring and releasing the lock.

synchronized is simpler and built into the Java language. When a thread enters a synchronized method or block, it acquires the object's intrinsic lock, and Java automatically releases it when the block or method exits. With Lock, we explicitly call lock() and unlock(), but in return we get more control, such as tryLock(), timed locking, interruptible locking, fairness options, and multiple Condition objects.

So I would normally use synchronized when simple mutual exclusion is enough, and choose Lock when I specifically need those additional locking features or more complex coordination.
```
Lock → Explicit synchronization mechanism from java.util.concurrent.locks.
ReentrantLock → Common implementation of Lock.
synchronized → Built-in Java locking mechanism using an object's intrinsic monitor.
synchronized → Lock acquisition/release handled automatically.
Lock → Must manually call lock() and unlock().
tryLock() → Try to acquire lock without waiting indefinitely.
Timed tryLock() → Wait for a specified amount of time.
lockInterruptibly() → Allows waiting thread to be interrupted.
Condition → More flexible waiting/signaling with Lock.
synchronized → Prefer for simple locking.
Lock → Use when advanced locking control is actually needed.
```

#### What is initial capacity of a Java collection?
Initial capacity is the amount of internal storage a collection is initially prepared to use before it needs to resize or expand. It is implementation-specific, so there isn't one default capacity for every Java collection. For example, an ArrayList can be created with an initial capacity such as new ArrayList<>(100). Setting an appropriate capacity can reduce the number of resizing and copying operations when we already know roughly how many elements the collection will hold.

Also, initial capacity and size are different: size is the number of elements currently stored, while capacity refers to the available internal storage.
```
Initial capacity → Internal storage prepared before growth/resizing.
No universal default → Capacity depends on the collection implementation.
ArrayList → Commonly described as capacity 10; modern Java allocates lazily.
HashMap → Default initial capacity 16.
Capacity ≠ size → Capacity = storage; size = current elements.
Why specify capacity? → Reduce resizing/copying when expected size is known.
new ArrayList<>(100) → Creates a list with initial capacity for about 100 elements.
```

#### What is load factor?
Load factor is the value that determines how full a hash-based collection, such as HashMap, can become before it resizes. The default load factor of HashMap is 0.75, so for an initial capacity of 16, the resize threshold is 16 × 0.75 = 12 entries. Once the threshold is reached, the map increases its internal capacity and redistributes the entries.

A higher load factor means better memory usage but potentially more collisions, while a lower load factor means fewer collisions but more memory usage. So 0.75 is a commonly used balance between memory and lookup performance.
```
Load factor → Decides how full a hash table can become before resizing.
HashMap default → 0.75.
Formula → threshold = capacity × load factor.
Capacity 16 + load factor 0.75 → threshold 12.
Reach threshold → HashMap resizes and redistributes entries.
Higher load factor → Better memory usage, potentially more collisions.
Lower load factor → More memory, potentially fewer collisions.
Load factor → Mainly relevant to hash-based collections.
```

#### When does a Java collection throw UnsupportedOperationException?
UnsupportedOperationException is thrown when we perform a collection operation that the particular collection or view does not support, most commonly a modification operation. For example, Arrays.asList() gives a fixed-size list, so add() and remove() throw UnsupportedOperationException, although set() is allowed. Similarly, Collections.unmodifiableList() or List.of() provides an unmodifiable collection, so modification operations are unsupported.

So I don't assume every List or Collection supports every modification method; the actual implementation determines which operations are supported.
```
UnsupportedOperationException → Operation exists in the API but isn't supported by that collection.
Common case → Calling add/remove/set on an unmodifiable or fixed-size collection.
Arrays.asList() → Fixed size; add/remove unsupported, set supported.
List.of() → Unmodifiable; modification operations unsupported.
Collections.unmodifiableList() → Modification through the returned view unsupported.
Reason → Collection implementation decides which optional operations it supports.
Runtime exception → Compiler allows the method call; actual collection rejects it.
```

#### What is difference between fail-safe and fail-fast iterators?
A fail-fast iterator detects structural modification during iteration and typically throws ConcurrentModificationException, as we commonly see with collections like ArrayList. This helps detect unsafe modification during traversal, although the behavior is best-effort.

The term fail-safe is commonly used for iterators that can continue even when the underlying collection is modified concurrently, but technically Java uses more precise terms depending on the collection. For example, CopyOnWriteArrayList provides snapshot-style iteration, while ConcurrentHashMap provides weakly consistent iterators. These are designed for concurrent access rather than throwing ConcurrentModificationException for every concurrent modification.
```
Fail-fast → Unexpected structural modification during iteration → typically ConcurrentModificationException.
Fail-fast example → ArrayList, HashSet, HashMap iterators.
Fail-fast → Best-effort detection, not a correctness guarantee.
"Fail-safe" → Common interview term, not an official Java category.
CopyOnWriteArrayList → Snapshot iterator; modifications don't affect current iterator.
ConcurrentHashMap → Weakly consistent iterator; may reflect some concurrent changes.
Iterator.remove() → Safe way to remove during iteration when supported.
Thread-safe ≠ fail-safe → They are different concepts.
```

#### What are atomic operations in Java?
An atomic operation is an operation that is performed as one indivisible unit, so another thread cannot observe it in a partially completed state. Atomic operations are important when multiple threads access shared data.

For example, count++ is not atomic because it involves reading, modifying, and writing the value separately. If multiple threads execute it at the same time, updates can be lost. Java provides atomic classes such as AtomicInteger, AtomicLong, and AtomicReference, which provide operations like incrementAndGet() and compareAndSet() for thread-safe updates without requiring a traditional synchronized block for each operation.
```
Atomic operation → Happens as one indivisible step.
count++ → NOT atomic; read + modify + write.
AtomicInteger → Provides atomic integer operations.
incrementAndGet() → Atomic increment.
compareAndSet() → Update only if current value equals expected value.
volatile → Visibility/order, NOT general atomicity.
synchronized → Lock-based way to protect operations.
Atomic classes → Commonly use CAS internally.
Use atomic operations → When multiple threads update shared state.
```

#### What is BlockingQueue in Java?
BlockingQueue is a thread-safe queue designed mainly for communication between producer and consumer threads. Its main feature is that operations can wait when the queue cannot immediately perform them. For example, take() waits when the queue is empty, and put() waits when a bounded queue is full.

It's commonly used in producer-consumer scenarios because it handles the waiting and thread coordination for us instead of requiring us to manually manage wait() and notify(). Common implementations include ArrayBlockingQueue, LinkedBlockingQueue, and PriorityBlockingQueue.

**Simple Producer-Consumer Example**
```
BlockingQueue<String> queue = new ArrayBlockingQueue<>(2);

Thread producer = new Thread(() -> {
    try {
        queue.put("Task 1");
        queue.put("Task 2");
        queue.put("Task 3");
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});

Thread consumer = new Thread(() -> {
    try {
        System.out.println(queue.take());
        System.out.println(queue.take());
        System.out.println(queue.take());
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});
```
The important part is what happens with "Task 3":
```
Task 1 → queue
Task 2 → queue
             ↓
        queue is full
             ↓
Producer waits
             ↓
Consumer takes Task 1
             ↓
Space becomes available
             ↓
Producer continues with Task 3
```

### Generics

#### What are Generics?
Generics allow us to write reusable and type-safe code that can work with different data types. The type is specified when we use the class, interface, or method, and the compiler checks that type for us.

For example, List<String> means the list is intended to contain only String objects, so if I try to add an Integer, I get a compile-time error. Generics are heavily used in the Collections Framework, but they can also be used with our own classes and methods to avoid duplicate code and reduce unnecessary type casting.
```
Generics → Write reusable code that works with different types.
Main benefits → Type safety + reusability + less casting.
List<String> → List restricted to String values.
<T> → Type parameter.
Generic class → Same class can work with different types.
Generic method → Same method can work with different types.
Collections → Heavily use generics.
Primitives → Cannot be used directly; use wrapper types like Integer.
Compile-time checking → Wrong type is usually caught by compiler.
Raw type → Collection used without generic type, e.g. List list.
```


#### Why do we need Generics? Can you give an example of how Generics make a program more flexible?
We need Generics mainly to make our code type-safe and reusable. Instead of writing separate classes or methods for different data types, we can write one generic implementation and specify the type when we use it.

For example, instead of creating separate StringBox, IntegerBox, and DoubleBox classes, I can create one Box<T> class. Then I can use Box<String>, Box<Integer>, or Box<Double> without changing the class itself. The compiler also checks the type for me, so I get errors at compile time instead of dealing with incorrect types at runtime.

This is why Generics are heavily used in the Collections Framework—for example, List<String>, Map<Long, User>, and Set<Integer> allow the same collection implementations to work safely with different types.
```
Why Generics → Type safety + code reuse + less casting.
Type safety → Wrong type is caught at compile time.
Reusability → One generic class/method works with many types.
Flexibility → Type can be specified when the class/method is used.
Without Generics → Often requires Object + explicit casting.
With Generics → Compiler knows the expected type.
Collections → List<String>, Map<Long, User>, Set<Integer>, etc.
Generic class → class Box<T>.
Generic method → <T> T method(...).
Primitives → Can't be used directly; use wrappers like Integer.
```

#### How do you declare a generic class?
To declare a generic class, we add one or more type parameters inside angle brackets after the class name. These type parameters act as placeholders for the actual types that will be provided when the class is used.

For example, class Box<T> declares a generic class where T can represent different types. I can then create Box<String> or Box<Integer> without creating separate classes for each type. This gives us code reuse while keeping type safety at compile time.
```
Generic class → Class that works with different types.
Declaration → class Box<T> { }
T → Type parameter/place-holder.
Usage → Box<String>, Box<Integer>, etc.
Multiple types → class Pair<K, V>.
K → Key, V → Value, T → Type, E → Element (common conventions).
Benefit → Code reuse + compile-time type safety.
```

#### What are the restrictions in using generic type that is declared in a class declaration?
When a generic type like T is declared at the class level, there are some restrictions. We cannot instantiate T directly using new T(), create a generic array like new T[], use the class-level T in static fields or static context, or use T with instanceof or as an exception type. Also, generic type arguments must be reference types, so primitives like int cannot be used directly; we use wrapper types like Integer. Most of these restrictions exist because Java implements generics using type erasure.
```
new T()           → ❌ Cannot instantiate type parameter
new T[]           → ❌ Cannot create generic array directly
static T field    → ❌ Class-level T cannot be used in static context
instanceof T      → ❌ Cannot check generic type at runtime
throws T          → ❌ Cannot use type parameter as exception type
Box<int>          → ❌ Primitives not allowed
Box<Integer>      → ✅ Use wrapper classes
```

#### How can we restrict Generics to a subclass of particular class?
We can restrict a generic type using a bounded type parameter with the extends keyword. For example, class Box<T extends Animal> means that T can be Animal or any subclass of Animal. This gives us type safety while also allowing the generic code to use the methods available in the bound type. For example, because T extends Animal, I can safely call eat() on a T object.

```
class Animal {
    void eat() {
        System.out.println("Eating");
    }
}

class Box<T extends Animal> {

    private T value;

    Box(T value) {
        this.value = value;
    }

    void process() {
        value.eat();   // ✅ Allowed
    }
}
```
```
Box<Dog> box = new Box<>(new Dog());       // ✅
Box<Cat> box2 = new Box<>(new Cat());      // ✅
Box<String> box3 = new Box<>("Hello");     // ❌
Quick Notes
Bounded generic → T extends Type
T extends Animal → Animal or its subclasses
Purpose → Restrict allowed types + access bound's methods
Class bound → T extends Animal
Interface bound → T extends Comparable<T>
Multiple bounds → T extends Animal & Serializable
```

#### How can we restrict Generics to a super class of particular class?
We use a **lower-bounded wildcard with `super`** when we want to restrict a generic type to a particular class or any of its superclasses. For example, `List<? super Integer>` allows `List<Integer>`, `List<Number>`, and `List<Object>`, but not `List<Double>`. This is mainly useful when the generic code needs to **consume or add values of a specific type safely**. In contrast, `extends` is used when we want a type that is a subclass of a given type.
```
super → lower-bounded wildcard
List<? super Integer> → Integer, Number, Object
extends → upper bound
super → lower bound
<T super Integer> → ❌ Invalid syntax
PECS → Producer Extends, Consumer Super
```

#### Can you give an example of a generic method?  
A generic method is a method that declares its own type parameter, so the method can work with different types while maintaining compile-time type safety. The type parameter is declared before the return type, for example, `public static <T> T getFirst(T[] array)`. When the method is called, Java can usually infer the actual type from the arguments. This makes the method reusable without needing separate versions for different data types.
```
Generic method → Method with its own type parameter
Syntax → <T> before return type
Example → public static <T> T getFirst(T[] array)
T can represent different types
Java often infers T automatically from arguments
Generic class and generic method are independent concepts
```

### Functional Programming

####  What is functional programming?
Functional programming is a programming style where we focus on processing data using functions rather than writing every step manually. Java introduced important functional programming features in Java 8, such as lambda expressions, functional interfaces, and the Stream API.

For example, if I want to filter even numbers from a list, I can use `filter()` with a lambda expression instead of writing a traditional loop. Functional programming can make data-processing code more readable and easier to compose. Concepts like pure functions and immutability also help make code more predictable. Java supports this style, although it is still a multi-paradigm language and is widely used for object-oriented programming too.
```
Functional Programming: A programming style that focuses on composing operations using functions.
Java 8: Introduced key functional programming features.
Lambda: Concise way to represent behavior.
Functional Interface: Interface with exactly one abstract method.
Stream API: Processes data using operations like filter(), map(), and sorted().
Pure Function: Same input produces the same output without side effects.
Immutability: Avoiding changes to existing data or objects.
Java: Supports both OOP and functional programming; it is not purely functional.
```
Let's understand with an example.

Traditional approach (imperative style):

Suppose we want to find all even numbers from a list.
```
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5, 6);

for (Integer number : numbers) {
    if (number % 2 == 0) {
        System.out.println(number);
    }
}
```
Here, we explicitly write the steps: loop through the list, check each number, and print the even numbers.

Functional approach:
```
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5, 6);

numbers.stream()
       .filter(number -> number % 2 == 0)
       .forEach(System.out::println);
```

#### What is a stream?
A Stream in Java is a way to process data from a source, such as a collection or an array, using operations like filtering, mapping, and sorting. It was introduced in Java 8 and is commonly used with lambda expressions.

For example, if I need to find even numbers from a list, I can use `filter()` instead of writing a loop manually. Stream operations are usually written as a pipeline, where intermediate operations like `filter()` and `map()` are followed by a terminal operation like `collect()` or `forEach()`. Intermediate operations are lazy, meaning they don't process the elements until a terminal operation triggers the pipeline.

A Stream doesn't store the data itself, doesn't normally modify its source, and cannot be reused after a terminal operation. It can also process data sequentially or in parallel when appropriate.


**A. Intermediate Operations**

These operations transform a stream and return another stream. They are generally lazy, meaning processing doesn't start until a terminal operation is called.

| Method       | Purpose                                  | Example                         |
| ------------ | ---------------------------------------- | ------------------------------- |
| `filter()`   | Select elements that satisfy a condition | Keep even numbers               |
| `map()`      | Transform each element                   | Convert names to uppercase      |
| `sorted()`   | Sort elements                            | Sort numbers in ascending order |
| `distinct()` | Remove duplicates                        | Keep unique numbers             |
| `limit()`    | Keep only a specified number of elements | Get the first three elements    |


**B. Terminal Operations**

These operations finish a stream pipeline by producing a result or performing an action.

| Method        | Purpose                                                |
| ------------- | ------------------------------------------------------ |
| `collect()`   | Collect results into a list, set, or another container |
| `forEach()`   | Perform an action for each element                     |
| `count()`     | Count the elements                                     |
| `reduce()`    | Combine elements into a single result                  |
| `findFirst()` | Retrieve the first element, if present                 |
| `anyMatch()`  | Check whether any element satisfies a condition        |

```
Stream: Processes data from a source using operations such as filtering and mapping.
Introduced: Java 8.
Source: Collection, array, or another supported data source.
Intermediate operations: Return another stream; usually lazy.
Terminal operations: Produce a result or perform an action.
Lazy evaluation: Processing starts when a terminal operation triggers the pipeline.
Stream does not store data itself.
Stream operations do not normally modify the source.
A stream cannot be reused after a terminal operation.
Sequential streams: Process without requesting parallel execution.
Parallel streams: Can process elements concurrently using multiple threads.
```
Example:
```
numbers.stream()
       .filter(n -> n > 3)
       .map(n -> n * 10)
       .collect(Collectors.toList());
```

#### What are intermediate operations in streams?
Intermediate operations are operations that transform or filter a stream and return another stream, allowing us to chain multiple operations together. Common examples are `filter()`, `map()`, `sorted()`, and `distinct()`. For example, I can use `filter()` to select specific elements and then `map()` to transform them.

An important point is that intermediate operations are lazy. They don't start processing elements until a terminal operation, such as `collect()` or `forEach()`, triggers the pipeline. This allows the Stream API to optimize how elements are processed.


| Operation    | Purpose                                                                     | Example                     |
| ------------ | --------------------------------------------------------------------------- | --------------------------- |
| `filter()`   | Keeps elements that satisfy a condition                                     | `filter(n -> n > 5)`        |
| `map()`      | Transforms each element                                                     | `map(n -> n * 2)`           |
| `sorted()`   | Sorts the elements                                                          | `sorted()`                  |
| `distinct()` | Removes duplicates                                                          | `distinct()`                |
| `limit()`    | Keeps at most the first `n` elements                                        | `limit(3)`                  |
| `skip()`     | Skips the first `n` elements                                                | `skip(2)`                   |
| `flatMap()`  | Transforms each element into a stream and flattens the results              | `flatMap(List::stream)`     |
| `peek()`     | Performs an action on elements as they pass through, commonly for debugging | `peek(System.out::println)` |


#### What are terminal operations in streams?
Terminal operations are operations that finish a Stream pipeline by producing a result or performing an action. Common examples are `collect()`, `forEach()`, `count()`, and `reduce()`. For example, I can use `filter()` to select even numbers and then `collect()` to store them in a new list.

Terminal operations trigger the execution of intermediate operations, which are normally lazy. Once a terminal operation has consumed a stream, that stream cannot be reused, so I need to create a new stream for another operation.

| Operation         | Purpose                                                         | Example                                 |
| ----------------- | --------------------------------------------------------------- | --------------------------------------- |
| `forEach()`       | Performs an action for each element                             | `stream.forEach(System.out::println)`   |
| `collect()`       | Collects elements into a collection or another result container | `stream.collect(Collectors.toList())`   |
| `count()`         | Returns the number of elements                                  | `stream.count()`                        |
| `reduce()`        | Combines elements into a single result                          | `stream.reduce(0, Integer::sum)`        |
| `findFirst()`     | Returns the first element, if present                           | `stream.findFirst()`                    |
| `anyMatch()`      | Checks whether at least one element matches a condition         | `stream.anyMatch(n -> n > 5)`           |
| `allMatch()`      | Checks whether every element matches a condition                | `stream.allMatch(n -> n > 0)`           |
| `noneMatch()`     | Checks whether no elements match a condition                    | `stream.noneMatch(n -> n < 0)`          |
| `min()` / `max()` | Finds the minimum or maximum element                            | `stream.max(Comparator.naturalOrder())` |

#### What are method references?
A method reference is a shorthand for a lambda expression when the lambda simply calls an existing method. We use the `::` operator to refer to that method.

For example, instead of writing `name -> System.out.println(name)`, I can write `System.out::println`. Both work with the functional interface expected by `forEach()`. Java supports references to static methods, instance methods, and constructors. Method references make code shorter and more readable, especially when working with the Stream API and functional interfaces.

| Type                                                            | Syntax                      | Example               |
| --------------------------------------------------------------- | --------------------------- | --------------------- |

| **Constructor reference**                                       | `ClassName::new`            | `ArrayList::new`      |


#### What are lambda expressions?
A lambda expression is a concise way to implement a functional interface without writing a full anonymous class. It was introduced in Java 8 and uses the `->` operator to separate parameters from the implementation.

For example, instead of creating an anonymous class to implement a `Runnable`, I can write `() -> System.out.println("Hello")`. Java determines the expected type from the context, so the lambda can be used wherever a compatible functional interface is expected. I commonly use lambdas with the Stream API for operations like filtering, mapping, and sorting collections. They reduce boilerplate code and make the intention of the code easier to understand.
```

Introduced: Java 8.
Operator: -> separates parameters from the implementation.

Benefits: Less boilerplate, more readable code, useful with Streams.
Single Expression: Can return a value implicitly.
Multiple Statements: Use {} and return explicitly when required.
Common Uses: Runnable, Comparator, Predicate, Consumer, Function, Stream API.
```

#### Can you explain the relationship between lambda expression and functional interfaces?
A functional interface and a lambda expression work together. A functional interface has exactly one abstract method, and a lambda expression provides the implementation for that method.

For example, if I have a `Calculator` interface with an `add(int a, int b)` method, I can implement it using `(a, b) -> a + b`. Java understands the parameter types and return type from the functional interface, so I don't need to specify them explicitly in the lambda.

The main benefit is that I can provide different implementations of the same interface without writing separate classes or anonymous classes. This reduces boilerplate code and is especially useful when working with the Stream API and other functional programming features in Java.

#### What is a consumer?
`Consumer<T>` is a functional interface from the `java.util.function` package that accepts one input and performs an operation without returning a result. Its main abstract method is `accept()`. ### Exception handling

#### Why is exception handling important?
Exception handling in Java is a mechanism for handling exceptional situations so that the application can respond properly instead of terminating unexpectedly. For example, if a program tries to divide a number by zero, Java throws an `ArithmeticException`.

We can handle that situation using `try` and `catch`. The `try` block contains the code that might fail, and the `catch` block handles the matching exception. We can also use `finally` for cleanup operations, such as releasing resources. In real-world applications, exception handling helps us manage failures, return meaningful error responses, and make sure resources are cleaned up properly. However, I avoid catching exceptions without handling them appropriately because that can hide the actual problem.

| Keyword   | Purpose                                                                                                          |
| --------- | ---------------------------------------------------------------------------------------------------------------- |
| `try`     | Contains code that might throw an exception.                                                                     |
| `catch`   | Handles a matching exception thrown from the associated `try` block.                                             |
| `finally` | Contains cleanup code that normally runs whether an exception occurs or not.                                     |
| `throw`   | Explicitly throws an exception.                                                                                  |
| `throws`  | Declares possible exceptions in a method signature, mainly to communicate or propagate exceptions to the caller. |
```
Exception Handling: Mechanism for responding to exceptional situations.
try: Contains code that may throw an exception.
catch: Handles a matching exception.
finally: Cleanup block that normally executes whether an exception occurs or not.
throw: Explicitly throws an exception.
throws: Declares exceptions that a method may propagate to its caller.
Checked Exception: Must be caught or declared under Java's exception rules.
Unchecked Exception: RuntimeException and its subclasses; catching or declaring isn't mandatory.
Error: Represents serious JVM/runtime problems.
Purpose: Handle failures, provide meaningful responses, and clean up resources.
Best Practice: Don't silently swallow exceptions; handle them appropriately.
```

#### What design pattern is used to implement exception handling features in most languages?
The design pattern commonly associated with exception handling is the Chain of Responsibility pattern. When an exception occurs, it can propagate up the call stack until a matching exception handler is found. Each level gets an opportunity to handle the exception; if it isn't handled there, it continues to the caller. 

For example, in Java, an exception thrown in a deeply nested method can be caught by a `try-catch` block in a method higher up the call stack. This resembles Chain of Responsibility, although exception handling is a built-in language feature rather than necessarily a direct implementation of that design pattern.

**Example in Java**
```
public class Main {

    static void method1() {
        method2();
    }

    static void method2() {
        method3();
    }

    static void method3() {
        int result = 10 / 0;
    }

    public static void main(String[] args) {
        try {
            method1();
        } catch (ArithmeticException e) {
            System.out.println("Exception handled in main()");
        }
    }
}
```
Output:

Exception handled in main()

*Here's what happens:*    
method1() calls method2().     
method2() calls method3().     
method3() throws an ArithmeticException.       
The exception propagates back through the calling methods until a matching catch block is found in main().
The exception is handled there.

This resembles Chain of Responsibility because the exception moves through successive levels until a handler takes responsibility for it.

```
Pattern: Chain of Responsibility.
Concept: Exception propagates up the call stack until a matching handler is found.
Java: Unhandled exceptions propagate to the calling method.
If no handler is found: The exception is uncaught and the thread may terminate.
Note: This is a conceptual association, not necessarily the internal implementation.
```
#### What is the need for finally block?
The `finally` block is used to execute cleanup code whether an exception occurs or not. For example, if I'm working with a file or another resource, I may need to ensure that it gets closed even if an exception occurs while processing it.

The `finally` block normally executes after the `try` and any matching `catch` block, including when the code returns from the method. However, it isn't guaranteed to execute if the JVM terminates abruptly. For resources that implement `AutoCloseable`, I generally prefer try-with-resources because it handles resource closure automatically.
```
finally: Used for cleanup code that should normally execute whether an exception occurs or not.
Execution: Runs after try/catch, including before a return completes.
Use cases: Resource cleanup and releasing resources.
Uncaught exception: finally executes normally, then the exception propagates.
Limitation: Not guaranteed if the JVM terminates abruptly.
Best practice: Prefer try-with-resources for AutoCloseable resources.
```

#### In what scenarios is code in finally not executed?
Although the `finally` block normally executes whether an exception occurs or not, there are some exceptions. For example, if `System.exit()` initiates JVM shutdown, `Runtime.getRuntime().halt()` terminates the JVM abruptly, or the JVM crashes, the `finally` block may not execute. It also won't be reached if execution gets stuck indefinitely inside the `try` block, such as in an infinite loop. So, I don't treat `finally` as an absolute guarantee that cleanup code will always run.


#### Is try without a catch is allowed?
Yes, a `try` block can exist without a `catch` block in Java, but a regular `try` statement must have a `finally` block if there is no `catch`. We can also use try-with-resources without `catch` or `finally`, because Java automatically closes the declared resources.

For example, if I use `try-finally` and an exception occurs, the `finally` block normally executes, but the exception still propagates because it hasn't been caught. So, `finally` is used for cleanup, not for handling the exception.

#### Is try without catch and finally allowed?
A normal `try` block cannot exist without either a `catch` or a `finally` block. However, Java allows a try-with-resources statement without `catch` or `finally`. In try-with-resources, Java automatically closes resources that implement `AutoCloseable`, even when an exception occurs. Any exception that isn't handled can propagate to the caller, so we may need to catch it or declare it using `throws`, depending on the exception type.
```
Normal try without catch/finally → ❌ Not allowed.
Try-with-resources without catch/finally → ✅ Allowed.
Try-with-resources → Automatically closes declared resources.
Unhandled checked exception → Must be caught or declared with throws.
```

#### Can you explain about try with resources?
Try-with-resources is a Java feature introduced in Java 7 that automatically closes resources when we finish using them. It is commonly used with files, database connections, and streams. The resource is declared inside the parentheses after `try`, and its class must implement `AutoCloseable` or a subinterface of it.

For example, when reading a file, I can declare a `BufferedReader` inside the try-with-resources statement instead of closing it manually in a `finally` block. Java automatically calls its `close()` method when the block exits, even if an exception occurs. This makes the code cleaner and helps prevent resource leaks.
```
Try-with-resources:
- Introduced in Java 7.
- Automatically closes resources after use.
- Resource must implement AutoCloseable or its subinterface.
- Resource is declared inside the parentheses after try.
- Closes resources even when an exception occurs.
- Multiple resources are closed in reverse declaration order.
- Can be used without catch or finally.
- Exceptions during closing may be recorded as suppressed exceptions.
- Common uses: Files, streams, database connections.
- Main benefit: Cleaner code and fewer resource leaks.
```

#### How does try with resources work?
Try-with-resources works by automatically closing resources when execution leaves the `try` block. The resource must implement `AutoCloseable` or one of its subinterfaces, and we declare it inside the parentheses after `try`.

For example, when reading a file, I can declare a `BufferedReader` inside the try-with-resources statement instead of closing it manually in a `finally` block. Java automatically calls its `close()` method, even if an exception occurs. Internally, the compiler generates the resource-cleanup logic, including handling exceptions that occur during closing. This makes resource management cleaner and helps prevent resource leaks.

```
Try-with-resources:
- Introduced in Java 7.
- Automatically closes resources when leaving the try block.
- Resource must implement AutoCloseable or its subinterface.
- Does not require a finally block just to close resources.
- Closes resources even when an exception occurs.
- Multiple resources close in reverse declaration order.
- If both the body and close() throw, the close exception is suppressed.
- Suppressed exceptions can be retrieved using getSuppressed().
- The compiler generates resource-cleanup logic.
- Main benefit: Cleaner code and fewer resource leaks.
```

#### Can you explain the hierarchy of exception handling classes?
In Java, the exception hierarchy starts with the `Throwable` class, which has two main subclasses: `Error` and `Exception`.

`Error` represents serious JVM or runtime problems, such as `OutOfMemoryError` and `StackOverflowError`. `Exception` represents conditions that an application may need to handle. Exceptions are further divided into checked and unchecked exceptions.

Checked exceptions, such as `IOException` and `SQLException`, must be caught or declared using `throws`. Unchecked exceptions are subclasses of `RuntimeException`, such as `NullPointerException` and `ArithmeticException`, and the compiler doesn't require us to catch or declare them. Understanding this hierarchy helps me decide how to handle failures and when an exception should propagate to the calling method.
```
Throwable: Root class of Java's throwable hierarchy.
Error: Serious JVM/runtime problems; unchecked.
Exception: Represents conditions applications may need to handle.
Checked Exceptions: Must be caught or declared with throws.
Examples: IOException, SQLException, ClassNotFoundException.
Unchecked Exceptions: RuntimeException and its subclasses.
Examples: NullPointerException, ArithmeticException, IllegalArgumentException.
Error and RuntimeException: Both unchecked.
Catch a superclass: Can catch exceptions belonging to its subclasses.
Best Practice: Catch exceptions you can meaningfully handle.
```

#### What is the difference between error and exception?
In Java, both `Error` and `Exception` extend the `Throwable` class, but they represent different types of problems. An `Error` usually indicates a serious JVM or runtime problem, such as `OutOfMemoryError` or `StackOverflowError`, and application code generally shouldn't try to recover from it. An `Exception`, on the other hand, represents a condition that the application may be able to handle, such as an `IOException` when reading a file or an `ArithmeticException` when dividing by zero.

Another important difference is that all `Error` subclasses are unchecked, whereas `Exception` includes both checked and unchecked exceptions. In practice, I handle exceptions when I can take meaningful action, but I generally avoid catching `Error` unless there is a specific reason.

```
Error: Usually a serious JVM/runtime problem; generally not handled by application code.
Exception: A condition that application code may be able to handle.
Hierarchy: Both Error and Exception extend Throwable.
Error examples: OutOfMemoryError, StackOverflowError.
Exception examples: IOException, SQLException, ArithmeticException.
Error: Always unchecked.
Exception: Can be checked or unchecked.
Best practice: Handle exceptions meaningfully; don't catch Error indiscriminately.
```

#### What is the difference between checked exceptions and unchecked exceptions?
The main difference between checked and unchecked exceptions is whether the compiler requires us to handle them or declare them using `throws`.

Checked exceptions are checked by the compiler, so we must catch them or declare them. For example, `IOException` can occur during file operations. Unchecked exceptions are subclasses of `RuntimeException`, and the compiler doesn't require us to catch or declare them. Examples include `NullPointerException` and `ArithmeticException`.

In practice, I handle checked exceptions when an operation can fail and the application needs a response. For unchecked exceptions, I also focus on preventing common problems through proper validation and correct coding rather than simply catching every exception.
```
Checked Exceptions:
- Compiler requires catch or throws.
- Examples: IOException, SQLException, ClassNotFoundException.
- Often associated with operations that can fail due to external conditions.

Unchecked Exceptions:
- Compiler doesn't require catch or throws.
- Subclasses of RuntimeException.
- Examples: NullPointerException, ArithmeticException, IllegalArgumentException.
- Often indicate invalid operations or programming mistakes.

Key Difference:
Checked → Compiler enforces handling or declaration.
Unchecked → Handling or declaration is optional.
```

#### How do you throw an exception from a method?
In Java, I use the `throw` keyword to explicitly throw an exception when a condition is not satisfied or an operation cannot proceed. For example, in a division method, I can check whether the denominator is zero and throw an `ArithmeticException` if it is. Once the exception is thrown, the method stops its normal execution, and the exception propagates to the caller until a matching handler is found or the exception remains unhandled.

I also distinguish between `throw` and `throws`: `throw` actually throws an exception object, while `throws` declares exceptions that a method may propagate. For checked exceptions, I must either handle them or declare them in the method signature.
```
throw:
- Used to explicitly throw an exception object.
- Example: throw new IllegalArgumentException("Invalid input");
- Stops normal execution of the current block and transfers control to exception handling.
- Exception propagates to the caller if not caught.

throws:
- Declares exceptions a method may propagate.
- Written in the method signature.
- Example: void readFile() throws IOException

Checked Exception: Must be caught or declared.
Unchecked Exception: Catching or declaring is not mandatory.
```

#### What happens when you throw a checked exception from a method?
When I throw a checked exception from a method, Java requires me to either handle it using `try-catch` or declare it using `throws` in the method signature. If I do neither, the code fails to compile.

For example, if my method throws an `IOException`, I can declare `throws IOException` and let the calling method handle it. The caller must also catch the exception or declare it using `throws`. So, `throws` allows an exception to propagate up the call stack; it doesn't handle the exception itself.
```
Checked Exception:
- Must be caught or declared using throws.
- If neither is done, compilation fails.
- throw → Actually throws an exception object.
- throws → Declares an exception that may propagate to the caller.
- The caller must also catch or declare the checked exception.
- Declaring an exception does not handle it.
```

#### What are the options you have to eliminate compilation errors when handling checked exceptions?
There are two main ways to resolve compilation errors caused by checked exceptions in Java.

The first is to handle the exception using a `try-catch` block. I use this when the current method can handle the failure or take appropriate action.

The second is to declare the exception using `throws` in the method signature, allowing it to propagate to the calling method. The caller must then catch it or declare it as well.

I choose between these approaches based on where the exception can be handled most appropriately. If the current method can recover from the problem, I handle it there; otherwise, I may propagate it to a higher level that has enough context to handle it.
```
Checked Exception — Two main options:

1. try-catch → Handle the exception in the current method.
2. throws → Declare the exception and allow it to propagate to the caller.

Important:
- Unhandled checked exceptions cause compilation errors.
- throws does not handle the exception.
- The caller must catch or declare the exception.
- Choose the handling location based on where the problem can be handled appropriately.
```

#### How do you create a custom exception?
In Java, I create a custom exception by extending either the `Exception` class or the `RuntimeException` class. If I extend `Exception`, it becomes a checked exception, so the caller must catch it or declare it using `throws`. If I extend `RuntimeException`, it becomes an unchecked exception, and the compiler doesn't require it to be caught or declared.

For example, in a banking application, I might create an `InsufficientBalanceException` and throw it when a withdrawal amount exceeds the available balance. I usually add a constructor that accepts an error message and passes it to the parent class using `super(message)`. This allows me to represent application-specific failures with meaningful exception types and messages.
```
Custom Exception: User-defined exception for application-specific errors.

Checked Custom Exception:
- Extend Exception.
- Must be caught or declared using throws.

Unchecked Custom Exception:
- Extend RuntimeException.
- Catching or declaring is not mandatory.

super(message):
- Passes the error message to the parent exception class.

throw:
- Throws the exception object.

throws:
- Declares exceptions that a method may propagate.

Common Example:
InsufficientBalanceException in a banking application.
```

#### How do you handle multiple exception types with same exception handling block?
In Java, we can handle multiple exception types in the same `catch` block using multi-catch, which was introduced in Java 7. We use the pipe (`|`) operator to specify the exception types. For example, `catch (NumberFormatException | ArithmeticException e)` handles either exception using the same block.

I use multi-catch when different exceptions require the same handling logic, because it avoids duplicating code. However, the exception types cannot have a parent-child relationship in a multi-catch statement. If different exceptions require different handling, I use separate `catch` blocks instead.


#### Can you explain a few exception handling best practices?
There are several best practices I follow when handling exceptions in Java.

First, I prefer catching specific exceptions instead of catching a broad `Exception`, unless I'm at a boundary where I have a proper strategy for handling unexpected failures. Second, I never swallow exceptions because that hides problems and makes debugging difficult. I either handle the exception meaningfully or let it propagate to the appropriate calling layer.

I also use try-with-resources for files and database-related resources so they are closed automatically. When wrapping an exception in a custom exception, I preserve the original cause to make debugging easier. I avoid using exceptions for normal program flow, provide meaningful error messages, and don't catch serious `Error` types indiscriminately.

The main goal is to make failures easier to understand and handle without hiding the actual problem or leaving resources open.
```
Exception Handling Best Practices

1. Catch specific exceptions whenever possible.
2. Never swallow exceptions; handle them or propagate them.
3. Use try-with-resources for AutoCloseable resources.
4. Catch exceptions at the layer that can handle them meaningfully.
5. Preserve the original cause when wrapping exceptions.
6. Don't use exceptions for normal control flow.
7. Provide meaningful exception messages.
8. Never log sensitive information.
9. Avoid catching Error or Throwable indiscriminately.
10. Don't log and rethrow at every layer; avoid duplicate logs.
11. Use custom exceptions for meaningful application-specific failures.
12. Validate input where appropriate, but don't assume validation prevents every failure.
```
